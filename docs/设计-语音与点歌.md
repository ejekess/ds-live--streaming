# 设计文档 · 语音回复与点歌翻唱

> 状态：**已定稿 · M1–M5 已实施**（券 5 分钟、T3 每日 3 首 / T4 每日 8 首，按建议值上线）
> 前置：`docs/项目文档.md` 里的骨架（源 → 总线 → 导演 → 舞台）。
> 本文覆盖新增的四件事：大模型改纯文本、语音合成、音频播放编排、点歌翻唱。
>
> **v2 修订**：按 2026-10-30 的确认，补入档位权益矩阵、点歌权（打赏解锁）、
> 敏感词两级过滤、唱歌动作占位，并新增 §8 状态模型、§9 数据流动。

---

## 1. 背景与目标

| 编号 | 目标 | 用户可感知的验收 |
| --- | --- | --- |
| G1 | 形象**开口说话** | 打开 `/avatar` 能听到她回应弹幕 |
| G2 | 打赏**解锁点歌**，她真的唱 | 送 T3+ 礼物后点歌，几十秒内听到 RVC 翻唱 |
| G3 | 互动**拟人化** | 开放式提问能接住，不再只会模板 |
| G4 | 安全边界**不后退** | 塞代码/算题/注入/敏感歌名，不执行、不播错、不烧钱 |

**三条贯穿始终的原则**：

1. **权限在宿主，不在模型**——模型永远不决定"执行什么"，只决定"怎么说"。
2. **模型只能收紧，不能放宽**——宿主判定不可唱，模型无权放行；宿主放行，模型可以拒绝。
3. **渲染与播放是两条时间线**——正在做歌不等于画面要空着。

---

## 2. 范围

**做**：语音合成与播放、点歌权与队列、翻唱渲染、大模型纯文本化、点歌意图识别、失败兜底、唱歌动作占位。

**不做**：实时变声、版权处理、多语言、音色切换 UI、外部消息队列、模型 function calling。

---

## 3. 关键决策

### 3.1 模型只返回一句话（不返回结构化意图）

| | |
| --- | --- |
| 决策 | 大模型输出纯文本，无 JSON、无 `intent` |
| 理由 | 消除"JSON 解析失败"这一必然发生的故障；少 ~20 tokens；模型专心说人话 |
| 代价 | 模型无法触发唱歌 → 由宿主判定（见 3.3） |

### 3.2 不给模型工具调用能力

模型没有 function calling / tools 参数。点歌由宿主代码触发，歌名经校验后传给它。
**一旦模型能调 `sing.py`，它就在决定执行本地程序，且参数可被注入。**

### 3.3 档位即权限：打赏解锁「点歌权」

| | |
| --- | --- |
| 决策 | 点歌不是随时可用的功能，而是**一次打赏换一次点歌机会**（点歌券，5 分钟有效、可叠加） |
| 理由 | 符合打赏经济；避免白嫖；"对应礼物级别只干对应事情" |
| 实现 | `songs/quota.mjs` 维护 `Map<viewerId, {credits, expiresAt}>`，落盘 |

### 3.4 内容审核两级，且模型只能收紧

```
L1 宿主硬筛（必过，100% 确定）：长度 / 字符集 / 黑名单 / 拼音归一化 + 谐音表
L2 模型软判（可选，只能收紧）：模型觉得不对劲，可以回"这首不太敢唱，换一首？"
                                → 但它无权把宿主已经拒绝的歌放行
```

| | |
| --- | --- |
| 决策 | 谐音/敏感词**主要靠宿主规则**（拼音 + 谐音映射），模型只做第二道软判 |
| 理由 | 谐音识别模型不稳定，且可被"这是我编的歌名啦"绕过；安全边界不能交给概率 |
| 对用户原意的回应 | "让大模型判断"仍然保留——只是它**只能更严格，不能更宽松** |

### 3.5 `max_tokens` 是安全网，不是省钱手段

钱在生成那一刻已产生；`max_tokens` 只封顶。`finish_reason === 'length'` 的正确用途是
**「这句被截断了，别上屏，换兜底台词」**。真正的省钱防线是调用次数上限（4/分钟、200/天）。
取 90 tokens（≈60 汉字）。

### 3.6 离线曲库优先，现场渲染有门槛

| 情况 | 行为 | 延迟 |
| --- | --- | --- |
| 曲库命中 | 立即排队 | 秒级 |
| 曲库未命中 + T4 以上 | 现场 RVC 渲染 | 1–5 分钟 |
| 曲库未命中 + T3 | **不渲染**，回"这首还没学会，换一首？" | 立即 |
| 未指定歌名 | 曲库随机（避开最近 3 首） | 秒级 |

### 3.7 固定短语：能预生成的预生成，带昵称的现合成

**一个必须说清的限制**：`behavior.mjs` 里的台词大多含 `{name}`。
**含变量的句子无法预生成**——总不能为每个观众名字各生成一条。

所以：

| 类型 | 处理 | 延迟 |
| --- | --- | --- |
| 不含变量的整句（"好耶""收到啦""开始咯"） | 预生成 mp3，直接播 | 0ms |
| 含 `{name}` / `{gift}` 的整句 | TTS 现合成 + **按文本哈希缓存** | 首次 ~300ms，之后 0ms |

"覆盖所有打赏台词"落地为：**覆盖所有不含昵称的句式**，含昵称的走缓存合成。
实测一句话合成 ~300ms，观众感知不到。

### 3.8 唱歌动作先占位

现有 8 个动作里没有"唱歌"。本期用 `aidale`（摇摆）+ `mood: happy` 占位，
并在 `stage` 里预留 `motion: 'sing'` 的槽位——后续加了新模型资源（举麦克风、音符流动）直接填。

### 3.9 队列不用外部 MQ

内存队列 + JSON 原子落盘 + 单 worker。理由见 §13.3。

## 4. 档位权益矩阵

「对应礼物级别只干对应事情」——严格按下表执行，不做跨级。

| 档 | 抖币 | 点歌权 | 指定歌名 | 曲库未命中 | 排队位置 | 每日上限 |
| --- | --- | --- | --- | --- | --- | --- |
| T1 小心意 | 0–1 | ✗ | — | — | — | — |
| T2 有份量 | 2–9 | ✗ | — | — | — | — |
| **T3 挺大方** | 10–99 | ✓ ×1 | ✓ | **拒绝**（不渲染） | 队尾 | 3 首 |
| **T4 大礼** | 100–2999 | ✓ ×1 | ✓ | **允许渲染** | 插到所有 T3 前 | 8 首 |
| **T5 重礼** | 3000+ | ✓ ×2 | ✓ + 可指定歌手 | 允许渲染 | **队首** | 不限 |

**三条辅助规则**：

1. **券有有效期**：打赏后 5 分钟内有效，过期作废（防止攒一堆券半夜刷屏）。
2. **同档位短时间内只发一张券**：同一用户 10 秒内的重复档位事件合并，发一张（防"送 10 朵玫瑰 = 10 张券"）。
   > 实现说明：抖音的 `groupId`（连击组）我没有解码，所以按「用户 + 档位 + 10 秒窗口」去重，
   > 不依赖连击组 id。这个规则比 `comboId` 稳，因为它只用到已解码的字段。
3. **无券点歌 → 只说话不执行**：模型说「想点歌要先送我个甜甜圈哦」，这一句由**话术层**生成，
   不消耗任何资源。

> 券的存储：`songs/quota.mjs` → `data/songs/quota.json`，按 `viewerId` 键，
> 记录 `{ credits, expiresAt, usedToday, day }`。进程重启不丢。

## 5. 模块拆分

原则：**一句话说不清它干什么，就是拆错了。**

| 模块 | 只做一件事 | 明确不做 | 依赖 |
| --- | --- | --- | --- |
| `voice/` | 文本 → 音频文件（带缓存） | 不决定何时说、不播放 | tts worker |
| `audio/` | 决定**此刻播什么**、谁压谁 | 不做合成、不做渲染 | 舞台 WS |
| `songs/quota` | 点歌券的发放与消费 | 不管队列、不管审核 | 文件 |
| `songs/gate` | 能不能点、这首能不能唱 | 不排队、不说话 | 黑名单/谐音表 |
| `songs/library` | 歌名 → 文件 | 不管排队、不管渲染 | 文件系统 |
| `songs/queue` | 请求的生命周期与持久化 | 不做渲染、不做播放 | 无 |
| `songs/render` | 歌名 → 成品文件 | 不排队、不播报 | RVC 子进程 |
| `interaction/songIntent` | 一句话是不是点歌、歌名是什么 | 不做决策、不上屏 | 无 |
| `brain/llm` | 一句话 → 一句话 | 不判意图、不调工具 | 模型 API |
| `director` | 编排：把谁触发谁串起来 | 不实现任何细节 | 以上全部 |

### 5.1 为什么把「门禁」单独拆出来

`quota`（有没有资格）和 `gate`（这首歌能不能唱）是**两个不同的问题**，失败话术也不同：

- 没资格 → "想点歌要先送我个甜甜圈哦"（引导打赏）
- 有资格但歌不能唱 → "这首我不太敢唱，换一首？"（拒绝内容）

混在一起写，两句话术会互相污染。拆开后各自可单测，且 `gate` 是纯函数。

### 5.2 依赖方向（单向，禁止反向）

```
   弹幕源 ──► bus ──► director ◄──► brain/llm
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   ┌─────────┐    ┌──────────┐     ┌──────────┐
   │ songs/  │    │ audio/   │     │ voice/   │
   │ service │    │ channel  │     └──────────┘
   └─┬─┬─┬─┬─┘    └────┬─────┘
     │ │ │ └─quota      │
     │ │ └───gate       ▼
     │ └─────queue  ┌─────────┐
     └───────library│ stage   │
        └──► render └─────────┘
```

**硬性规则**（Review 时按此卡）：

1. `songs/**`、`voice/**`、`audio/**` 不得 import `director` / `server` / `stage`。
2. `stage/` 只认 `{type:'audio'|'act'|'effect'}`，不知道歌名从哪来。
3. `brain/` 不 import 任何 `songs/`——模型永远不知道"点歌"这回事。
4. 只有 `director` 可以同时 import 多个领域模块。

## 6. 接口契约

### 6.1 门禁与券

```js
// quota.mjs —— 纯数据，无 IO 副作用（load/save 显式调用）
quota.grant(viewerId, tier);      // 按档位发券，返回 {credits}
quota.take(viewerId);             // 消费一张，返回 boolean
quota.peek(viewerId);             // 剩余额度（给话术用）

// gate.mjs —— 纯函数
gate.checkSong('晴天', { tier, source });
// → { ok:true } | { ok:false, reason:'blacklist'|'homophone'|'too_long'|'bad_chars' }
gate.suggestRange(tier);          // → { allowRender:boolean, maxQueue:number }
```

### 6.2 点歌服务

```js
const songs = await createSongService(cfg.songs, { voice, audio });

await songs.request({ song: '晴天', user, tier });
// → { ok:true, id, position:1, immediate:true, etaMs:15000 }
// → { ok:false, reason:'no_credit'|'queue_full'|'rejected', hint:'...' }
```

### 6.3 音频通道

```js
audio.playVoice({ file, durationMs, id });
audio.playMusic({ file, durationMs, id });
audio.duck(true);    // 音乐压到 30%
audio.state();       // → { mode, music, voice }
```

### 6.4 舞台契约（新增）

```jsonc
// 服务端 → 舞台
{ "type":"audio", "track":"voice", "src":"/media/voice/8f3a.mp3", "id":"v_12", "gain":1.0 }
{ "type":"audio", "track":"music", "src":"/media/songs/qingtian.mp3", "id":"m_7", "gain":1.0, "loop":false }
{ "type":"audio", "track":"music", "action":"duck", "gain":0.3 }
{ "type":"audio", "track":"music", "action":"stop" }

// 舞台 → 服务端（必须回报，否则 15s 超时强制推进）
{ "type":"audio-done", "id":"m_7", "reason":"ended" }   // ended | error | skipped
```

**幂等**：同一个 `id` 重复下发，舞台忽略第二次。

## 8. 状态模型

这一节是本次修订的重点。**所有状态都必须能持久化、能恢复、能被管控台读到。**

### 8.1 全局状态（单例，由 director 持有）

```js
systemState = {
  source:      'idle' | 'running' | 'stopped',      // 弹幕源
  stage:       'connecting' | 'ready' | 'lost',     // 舞台 WS
  performance: 'idle' | 'acting',                   // 形象演出（busyUntil）
  audio:       'silent' | 'speaking' | 'singing',   // 音频模式
  queue:       { size, rendering, playing },        // 队列概览
}
```

**状态推导规则**（不手工设，避免不一致）：

| 状态 | 由什么推导 |
| --- | --- |
| `audio.mode` | 有 music 在播 → `singing`；否则有 voice → `speaking`；否则 `silent` |
| `performance` | `now < busyUntil` |
| `stage` | WS 连接状态 + 最近一次 ack 时间（>20s 无 ack → `lost`） |

### 8.2 实体状态：点歌请求

```
queued ──claim──► rendering ──ok──► ready ──announce──► announcing ──► playing ──► done
   │                  │                 ▲                                     │
   │                  └──fail──► failed │                                     │
   └──────────reject（资格/审核）──► rejected                          error ─┘
```

| from | to | 触发 | 副作用 |
| --- | --- | --- | --- |
| — | `queued` | 门禁通过 + 有券 | 扣券、写盘、立刻播"正在安排" |
| `queued` | `rendering` | worker 取到（曲库未命中） | spawn 子进程，记 `startedAt` |
| `queued` | `ready` | worker 取到（曲库命中） | 直接指向曲库文件 |
| `rendering` | `ready` | 子进程退出 0 | 记 `file`、`durationMs`、归一化响度 |
| `rendering` | `failed` | 非 0 / 超时 / retries 耗尽 | 播道歉语音，`error` 落盘 |
| `ready` | `announcing` | 轮到播放 + 曲目间隙 ≥ 90s | 播报幕语音，记 `announcedAt` |
| `announcing` | `playing` | 报幕语音结束 + 静默 1.5s | 下发 `audio music`，形象切"唱歌"动作 |
| `playing` | `done` | 舞台回报 `audio-done` | 形象回到待机 |
| `playing` | `failed` | 舞台回报 `error` / 15s 无回报 | 播道歉，继续下一首 |

**非法跃迁**（必须抛错，不能静默）：`done → playing`、`failed → ready`、`queued → playing`。

**崩溃恢复**（启动时扫 `queue.json`）：

| 落盘状态 | 恢复为 | 理由 |
| --- | --- | --- |
| `queued` | 保持 | 没动过 |
| `rendering` | `queued`，`retries+1` | 子进程随进程死了，重来 |
| `ready` | 保持 | 文件还在，可直接播 |
| `announcing` | `ready` | 报幕被打断，重新报 |
| `playing` | `ready` | 歌可能只播了一半，重新播一遍更自然 |
| `retries > 2` | `failed` | 放弃，别再卡队列 |

### 8.3 实体状态：语音片段

```
pending ──缓存命中──► ready ──► playing ──► done
   └──需合成──► synthesizing ──ok──► ready
                    └──fail──► failed（调用方决定：不说话 or 换固定短语）
```

**抢占规则**：`playing` 中的 voice 被新 voice 顶掉时，旧的回 `done(skipped)`，
不计入播放次数。**music 不受影响，只 duck。**

### 8.4 实体状态：观众额度

```js
{ credits, expiresAt, usedToday, day }
```

| 事件 | 变化 |
| --- | --- |
| 收到 T3 礼物 | `credits += 1`，`expiresAt = now + 5min` |
| 收到 T4/T5 礼物 | `credits += 1`（T5 为 +2），同上 |
| 同档位连击 | **不重复发券**（按 `comboId` 去重） |
| 点歌成功 | `credits -= 1`，`usedToday += 1` |
| 跨天 | `usedToday` 归零（惰性计算，读时判断 `day`） |
| 券过期 | `credits` 作废（读时判断 `expiresAt`） |

## 9. 数据流动

### 9.1 消息总表（谁产生、谁消费、丢了会怎样）

| # | 消息 | 产生者 | 消费者 | 频率 | 丢失后果 |
| --- | --- | --- | --- | --- | --- |
| 1 | `LiveEvent` | 弹幕源 | bus → director | 高 | 丢一条弹幕：无感 |
| 2 | `SongRequest` | director | songService | 低 | 点歌丢失：观众会问 |
| 3 | `QueueEvent` | queue | director | 低 | 不播报：体验断层 |
| 4 | `AudioCommand` | audio | stage | 中 | **静音**（必须重试或超时推进） |
| 5 | `StageAck` | stage | audio | 中 | 队列卡住（15s 超时兜底） |
| 6 | `VoiceCommand` | director | voice | 中 | 不说话（可降级为气泡） |
| 7 | `TtsResult` | voice | director/audio | 中 | 同上 |

**关键**：#4 和 #5 是**唯一有状态耦合**的一对，必须成对设计（id + 超时）。

### 9.2 主链路：一条弹幕进来

```
[1] source.emit([CommentEvent])
      │  { type:'comment', user:{id,name}, text }
      ▼
[2] bus.emit('live') ──► 管控台事件流
      ▼
[3] director.handle()
      ├─► stage.push({type:'feed'})                    ← 弹幕流水立刻上屏
      └─► selector.offer(ev)                           ← 进候选池
      ▼
[4] 每 1.2s：selector.pick() → { ev, text }
      ▼
[5] songIntent.parseSongRequest(text)                  ← 纯函数，先判点歌
      ├─ isRequest ──► §9.3 点歌链路
      └─ 否 ──► [6]
      ▼
[6] brain.reply({ text, user })
      ├─ intent=truncated ──► 兜底台词
      └─ 正常 ──► [7]
      ▼
[7] voice.speak(reply) ──► { file, durationMs }
      ├─ audio.playVoice(...)                          ← 出声
      └─ stage.push({type:'act', line: reply})         ← 气泡 + 口型
```

### 9.3 点歌链路（含门禁与两级审核）

```
[1] songIntent → { isRequest:true, song:'晴天' }
      ▼
[2] quota.take(userId) ── 无券 ──► 话术："想点歌要先送我个甜甜圈哦"
      │                                （不消耗任何资源，结束）
      ▼ 有券
[3] gate.checkSong(song, {tier}) ── 不过 ──► 话术："这首我不太敢唱，换一首？"
      │                                        （券退回，记审计日志）
      ▼ 过
[4] library.find(song)
      ├─ 命中 ──► queue.request(source:'library') ──► [6]
      └─ 未命中
            ├─ tier < 4 ──► 话术："这首还没学会，换一首我会的？"（券退回）
            └─ tier >= 4 ──► queue.request(source:'render') ──► [6]
      ▼
[6] queue.request() → { ok, id, position, immediate }
      ▼
[7] 立刻播反馈（1 秒内）：
      ├─ immediate ──► "海盐汽水点的晴天，这就安排～"
      └─ 需渲染 ────► "这首我还没学会，正在学，等我几分钟～"
```

### 9.4 worker 与播放（两条独立时间线）

```
        ┌────────── 渲染时间线（慢，1–5 分钟） ──────────┐
        │ 每 3s 轮询 queue.claimNext()                  │
        │   ├─ 曲库命中 → markReady                    │
        │   └─ 需渲染   → spawn sing.py（超时 10min）   │
        │                  ├─ 成功 → markReady          │
        │                  └─ 失败 → markFailed + 道歉  │
        └───────────────────┬───────────────────────────┘
                            │ 队列状态变化
                            ▼
        ┌────────── 播放时间线（快，秒级） ─────────────┐
        │ audio 空闲 && 距上首 ≥90s                     │
        │   → 取 ready 里优先级最高的                    │
        │   → announcing：voice.speak("接下来播放…")     │
        │   → 静默 1.5s                                 │
        │   → playing：audio.playMusic + 形象切动作      │
        │   → 等 audio-done → done                      │
        └───────────────────────────────────────────────┘
```

**要点：渲染慢不阻塞播放。** 正在渲染 A 的同时，曲库里的 B 可以照常播。

### 9.5 竞态与裁决

| 竞态 | 裁决 |
| --- | --- |
| 两人 5 分钟内点同一首 | 队列层面合并：复用 `ready` 文件，报幕念两个人的名字 |
| 渲染中来了 T5 插队 | 插队只影响 `queued` 的顺序，**不影响正在 `rendering` 的** |
| 语音正在播，又来一条更重要的 | 新 voice 顶掉旧 voice；music 只 duck 不打断 |
| 唱歌中来了礼物演出（Live2D 动作） | 动作可以叠（形象手舞足蹈），**音频不打断** |
| 舞台断线重连 | 重连后推 `audio-state` 快照；正在播的歌**从头续播**（不做断点续传） |
| 同一首歌连续被点 | `minGapMs=90s` 内不重复播；曲库随机时避开最近 3 首 |
| 队列满（>5） | `{ok:false, reason:'queue_full'}` → "排队有点多，等我唱完这两首" |

## 12. 技术选型

| 决策点 | 选择 | 理由 | 否决方案 |
| --- | --- | --- | --- |
| TTS | 常驻 Python worker（复用已装 `edge_tts`） | 音色与已有语音库一致；单句 200–400ms | `msedge-tts` npm 包（音色不一致风险）；浏览器 `speechSynthesis`（无法缓存） |
| 播放 | 舞台两个 `<audio>` + 音量渐变 | 原生、零依赖、duck 精确 | Web Audio API（状态更多） |
| 队列持久化 | JSON + 原子写（tmp → rename） | 几十条、人眼可读、零运维 | Redis / SQLite |
| 渲染 | `spawn` + 超时 kill | 天然隔离，RVC 崩了不带走主进程 | 进程内调 Python |
| 意图/门禁 | 纯函数（正则 + 拼音归一化） | 可单测、零成本、100% 可预测 | 模型分类 |
| 新依赖 | **0 个 Node 包** | — | — |

### 12.1 谐音怎么处理（先简单，别过度设计）

分三步做，**按需升级**：

| 级别 | 做法 | 成本 | 何时上 |
| --- | --- | --- | --- |
| L1（默认） | **精确黑名单**：把敏感词和它的常见谐音写法都显式列出来（如「鸡你太美 / 只因你太美 / ji ni tai mei」） | 0，一个数组 | 现在就够 |
| L2（可选） | 拼音归一化：中文转全拼 + 模糊音折叠（zh↔z, ch↔c, sh↔s, n↔l） | 一张常用字表（~40KB）或加 `pinyin-pro` 依赖 | 黑名单维护不动了再上 |
| L3（不做） | 语义级谐音识别 / 交给模型判断 | 高且有不确定性 | 不做 |

**原则：宁可漏，不可错杀。** 把《晴天》误判成敏感歌，比漏掉一个梗歌更伤体验。

模型在这里的位置是**第二道软判**：宿主放行的歌，模型可以觉得不对劲而拒绝（"这首我不太敢唱"）；
宿主已经拒绝的，模型无权放行。

## 13. 失败模式与降级

| 场景 | 检测 | 降级 |
| --- | --- | --- |
| TTS 合成失败 | worker 返回 error / 超时 5s | 不发声，改为纯气泡（保底可见） |
| 固定短语缺失 | 文件不存在 | 走实时合成 |
| 模型截断 | `finish_reason=length` | 丢弃半句，播兜底台词 |
| 模型超时/断网 | `AbortSignal` 6s | 回退规则脑 |
| 曲库文件损坏 | 启动校验大小/可解码 | 剔除索引 + 告警 |
| 渲染失败 | 非 0 / 超时 | 语音道歉 + `failed`，队列继续 |
| 队列满 | `items ≥ max` | "排队有点多" |
| 舞台无响应 | 15s 未回报 | 强制推进 |
| 进程崩溃 | 启动扫描 | 按 §8.2 恢复表处理 |
| 券发放异常（连击） | 按 `comboId` 去重 | 只发一张 |

**实施中改掉的三个设计判断**：

1. **TTS 传输要双通道**。常驻 worker 走管道最快（300ms），但某些环境禁止管道 stdio（EPERM），
   于是加了「一次性子进程 + 文件通信」的兜底，慢（1.7s）但不丢功能。
2. **气泡必须先出、语音后补**。原设计是合成完再推 `act`，结果受限环境下观众会先看到
   两秒静默再突然开口。改成「气泡立刻上屏 + 音频异步补」，观感正常。
3. **报幕要等「说完」而不是「开始说」**。原来按固定 1.5s 计时，长句子会被歌压住；
   现在监听 `audio-done` 再留 1.5s 空白。

### 20.1 实施后补的两条语义修正

**① 曲库必须是「成品翻唱库」。** 最初把 `libraryDir` 指向了 `qq-bridge/rvc/songs`（原曲库），
结果点歌放出来的是周杰伦原唱——那是素材，不是翻唱。现在：

| 目录 | 角色 |
| --- | --- |
| `data/songs/covers` | **成品翻唱库**（点歌先查这里） |
| `qq-bridge/rvc/songs` | 原曲素材，只给 `sing.py` 用，本项目不扫描 |
| `data/songs/rendered` | 渲染临时产物 |

**成品自动入库**：渲染成功后复制进 covers 并更新索引，同一首第二次点就是秒播。

**② 没有舞台在看不合成语音。** 实测 107 分钟里 699 次播放有 **452 次靠 15 秒超时推进**，
因为舞台页没开、没人回执。现在 `#voiceFor` 先看 `stage.hasClients()`，没人听就不合成。
